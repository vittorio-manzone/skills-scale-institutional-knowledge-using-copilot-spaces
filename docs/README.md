# OctoAcme Project Management Docs

This collection describes OctoAcme's lightweight, iterative approach to delivering product work. Initiation starts by validating the business need, defining measurable outcomes, identifying stakeholders and risks, and making a go/no-go decision. Once approved, the team plans the work as a prioritized, estimable backlog with clear acceptance criteria and a Definition of Done, while mapping milestones, dependencies, and risks.

During execution, teams deliver small increments and track work on a shared project board. Pull requests link work to issues and acceptance criteria, receive review, and pass CI checks before merging. Teams report progress and risks regularly, review dependencies, and escalate blockers from the team to the PM, Product Lead, and sponsor as needed. Before release, the team checks readiness, acceptance criteria, and CI results; prepares release notes and a rollback or mitigation plan; tests in staging; verifies deployment; and communicates the release to stakeholders.

The PM coordinates delivery, schedules, risks, and communication; the Product Manager owns outcomes and backlog priorities; developers implement and test the work; QA validates quality and acceptance criteria; and stakeholders provide input and approvals. Communication includes PM–Product Manager alignment, delivery-team standups, weekly status or delivery syncs, monthly stakeholder updates, and demos at sprint or milestone ends. Quality practices include unit tests for new logic, integration tests where applicable, end-to-end smoke tests for critical flows, CI lint/test/security checks, and release smoke tests. Retrospectives after sprints, releases, milestones, or incidents turn lessons into owned, tracked actions.
